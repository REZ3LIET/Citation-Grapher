# Citation Graph Application — Implementation Plan

## 1. Product objective and delivery target

Build a local-first **research literature discovery tool** for researchers who
already have several relevant papers and want to find additional publications,
especially recent work, connected to those seeds by citations. The citation
graph is the discovery mechanism and exploration interface; bibliometric
analysis and reconstruction of a complete historical citation network are not
the primary objectives.

The application accepts at least one seed paper, one or more guiding topics,
and an inclusive publication-year range. It prioritizes discovering previously
unknown papers, showing relationships among retained publications, supporting
topic-assisted exploration, and exporting reproducible datasets for later
analysis. It does not rank papers as influential or foundational in the MVP.

Version 1 must work without API keys, paid services, subscriptions, or user
authentication. Public OpenAlex functionality is the primary metadata and
citation source. arXiv metadata and publicly accessible PDFs provide graceful
fallbacks where applicable. Any other public scholarly lookup is used only when
technically feasible and permitted by its terms; failure of a fallback must not
terminate the whole run.

### Fixed policies

- Citation directions: backward, forward, or both; default both.
- Expansion depth: 1–3 hops, default 1.
- The year range is a hard inclusion constraint at every expansion step.
- Guiding topics annotate papers; they never prune discovery or the canonical
  graph.
- At 500 unique, year-eligible papers, discovery pauses and requires an explicit
  continue action.
- After continuation, discovery stops at 1,000 unique papers. The run is marked
  `partial_limit_reached`, and all papers and citations collected so far remain
  available for exploration and export.
- Discovery state is checkpointed to disk and a paused or interrupted run can be
  resumed after restarting the application.
- Candidate collection is bounded to protect keyless providers. Default budgets
  are three pages and 600 raw candidates per parent paper/direction, 10,000
  pending candidates per BFS depth, and 1,500 provider requests per run. These
  operational values are configurable, but a reached budget is never silent: it
  marks the affected frontier and run as retrieval-incomplete.

The backend serves JSON APIs while the frontend owns visualization state. A
single local worker claims durable jobs from SQLite; leases and idempotent state
transitions prevent duplicate work after a restart. The two canonical CSV files
are generated by the backend and can also be uploaded to the explorer without
starting a discovery run or issuing scholarly API requests.

## 3. Domain model and canonical data

### Paper

Each paper receives a stable internal ID. Identity resolution uses the following
precedence:

1. Normalized DOI.
2. OpenAlex work ID.
3. arXiv ID where available.
4. Conservative normalized-title match, accepted only with supporting metadata
   such as compatible year and author.

Fields include internal ID, provider IDs, title, authors, publication year,
venue, abstract, DOI, publication URL, seed flag, discovery depth, discovery
direction and provider provenance, contributing seed frontiers, topic labels and
scores, provider-reported citation count, and internal citation counts.

### Citation

A citation is a directed pair from citing paper to cited paper. Its uniqueness
key is `(citing_paper_id, cited_paper_id)`. It records provider provenance,
retrieval timestamp, and optional context. OpenAlex does not normally provide
citation context, so that field is empty in v1.

### Run

A run records configuration, status, counters, warnings, provider details,
timestamps, unresolved seeds, metadata exclusions, API failures, pagination
restrictions, checkpoints, and whether a warning or hard limit was reached.

Run statuses:

```text
created -> resolving -> collecting_frontier -> scheduling_frontier
        -> awaiting_continue -> completing_edges -> annotating -> exporting
        -> completed | completed_partial

Any active state may become failed or stopping. A stopped run proceeds through
completion, annotation, and export before ending as completed_partial.
```

Stage and outcome are stored separately. Final outcomes distinguish a fully
processed attempted traversal, a user-stopped run, a provider-limited run, and
an application-limit run. Reaching 1,000 sets the outcome reason to
`partial_limit_reached`, but the run still proceeds through edge completion,
annotation, and export for the retained set whenever possible.

### Persistent checkpoint model

SQLite stores resolved seeds, canonical papers, citations, per-depth/per-seed
frontiers, retrieved and pending candidates, processed identifiers, provider
pagination cursors, request outcomes, warnings, failures, and provenance. State
changes are transactional at provider-page and candidate-acceptance boundaries.
On startup, the worker reclaims expired job leases and resumes from the last
committed boundary; inserts and edge writes are idempotent. The exact 500-paper
pause survives process and machine restarts.

### Canonical files

- `papers.csv`: one row per canonical included paper.
- `citations.csv`: one row per unique directed edge whose endpoints both exist
  in `papers.csv`.
- `run_metadata.json`: configuration, status, discovery and coverage statistics,
  provider/version information, warnings, unresolved inputs, exclusions,
  failures, pagination limitations, and completeness indicators.
- `graph.graphml`: optional interoperable export derived from the two CSV
  datasets.

CSV columns and their encodings will be documented and covered by schema tests.
Topics, scores, and authors use JSON arrays inside quoted CSV fields to avoid
ambiguous delimiter conventions.

## 4. Discovery pipeline

### Step 1: Validate configuration

- Require at least one non-empty seed input and at least one topic.
- Require integer years with minimum no greater than maximum.
- Accept depth 1–3 and a supported citation direction.
- Normalize and deduplicate identical seed strings before resolution, while
  requiring at least one resolved seed.

### Step 2: Resolve seeds

Recognize DOI, OpenAlex ID/URL, arXiv ID/URL, ordinary publication URL, and PDF.
DOI and OpenAlex identifiers are resolved directly. arXiv identifiers use public
arXiv metadata as a fallback when OpenAlex resolution is unavailable. Publication
URLs use embedded scholarly metadata where permitted, followed by conservative
public lookup. Publicly accessible PDFs are processed locally with GROBID to
extract metadata and reference strings; extracted references are resolved to
canonical identifiers conservatively. PDF extraction can add backward citation
candidates but cannot independently discover forward citations.

Every unresolved seed produces a user-visible error. Seeds outside the range are
reported as exclusions rather than silently included. Discovery starts when at
least one seed resolves successfully and satisfies the year constraint; other
unresolved or excluded seed inputs remain in run metadata.

### Step 3: Collect and schedule BFS frontiers

Traversal is breadth-first. No depth `d + 1` candidate is accepted until all
retrievable, eligible depth `d` candidates have been collected and scheduled,
or retrieval for part of depth `d` has been explicitly recorded as incomplete.

For each depth and originating seed frontier:

1. Fetch configured backward references and/or forward citations. When both are
   selected, complete bounded forward lookups across the level before beginning
   bibliography-heavy backward resolution. OpenAlex
   reference IDs supply backward candidates; filtered citing-work queries supply
   forward candidates. arXiv metadata and locally parsed public PDFs provide
   metadata and backward-reference fallbacks only.
2. Retry throttling and transient provider failures with bounded exponential
   backoff, charging every attempt to the durable request budget. Persist every
   provider page, cursor, failure, and pagination restriction.
   Stop collection at the configured per-query page/candidate budget, per-depth
   pending-candidate budget, or run-wide request budget. Persist the next cursor
   where available and classify the stop as `application_collection_budget`.
3. Apply the inclusive year filter in provider queries where possible, then
   verify locally. Papers with missing years are excluded and logged.
4. Resolve canonical identifiers and merge forward and backward candidates.
   Deduplicate globally while retaining every discovery direction, parent,
   provider, depth, and contributing seed frontier as provenance.
5. Within each seed frontier, order candidates by provider-reported citation
   count ascending, publication year descending, then stable canonical
   identifier ascending. Missing citation counts sort after known counts. This
   is a traversal heuristic intended to surface less-obvious papers; it is not a
   relevance, quality, or influence score.
6. Interleave the sorted seed-frontier queues with deterministic round-robin
   scheduling. A candidate contributed by multiple frontiers is accepted once,
   all contributions are recorded, and the round-robin advances. This prevents
   one seed's large neighborhood from monopolizing a truncated run.
7. Add accepted candidates to the next-depth frontier and expand only while the
   current paper depth is less than the configured maximum.

Sorting occurs over candidates actually retrieved for the sealed depth
frontier. If a provider returns only a partial frontier, blocks pagination, or
fails after retries—or an application collection budget is reached—the
scheduler never implies global ordering: it records that ordering and traversal
completeness apply only to retrieved candidates.
Transient failures use bounded exponential backoff and `Retry-After`; provider
adapters use bounded concurrency and descriptive identification without
requiring contact details or credentials.

The traversal checks the unique included-paper count after every accepted paper:

1. On accepting the 500th paper, persist the remaining ordered candidates,
   frontier rotation position, BFS depth, and pagination state; set
   `awaiting_continue`; and stop processing. This makes 500 an exact,
   restart-safe pause boundary.
2. If the user chooses Stop and Export, record outcome reason `user_stopped` and
   finalize the retained graph, annotations, and exports as a partial run.
3. If the user continues, resume the queue.
4. On accepting the 1,000th paper, persist counts and provenance for unprocessed
   candidates, stop discovery, retain valid edges between accepted nodes,
   record a hard-limit warning, and finalize the run with outcome reason
   `partial_limit_reached`.

### Step 4: Complete internal edges

After expansion stops, inspect available citation data for every retained paper
and add each retrieved directed citation for which both endpoints are in the
retained node set. This pass runs for completed, user-stopped, provider-limited,
and hard-limited runs. It does not introduce new papers, and it preserves citing
to cited direction.

For every paper/direction attempted, metadata records success, failure, partial
pagination, or unsupported retrieval. Edge-completion status is therefore
reported as complete relative to successful attempted retrieval or incomplete;
it is never described as proof that all real-world citations were found.

### Step 5: Annotate topics

- Build embeddings locally from each topic and each paper's title plus abstract.
- Compute cosine similarity independently for every paper/topic pair.
- Store all relevance scores and assign zero or more labels using a configurable
  threshold.
- If both title and abstract are insufficient for meaningful scoring, mark the
  paper `unclassified` and do not infer labels.
- Cache topic embeddings within a run and process paper texts in batches.

The initial embedding model should be small enough for local CPU use. Its exact
name, version, threshold, and normalization settings are recorded in run
metadata so exports are reproducible. Similarity values are displayed as
heuristic indicators, not calibrated probabilities.

### Step 6: Validate and export

- Assert unique paper IDs, unique directed edges, and referential integrity.
- Compute internal in-degree and out-degree.
- Write files atomically to `data/runs/<run_id>/`.
- Build optional GraphML from the canonical CSV-equivalent records when that
  export is requested.
- Surface partial data and warnings even when individual metadata requests fail.

### Step 7: Report discovery quality

`run_metadata.json` reports:

- input seed count, resolved seed count, and per-seed resolution outcomes;
- discovered-paper count excluding seeds and accepted papers at each BFS depth;
- forward and backward candidate counts before and after deduplication;
- accepted-paper contributions from each seed frontier, including shared credit;
- exclusions by year, missing year, insufficient identity, and other metadata;
- API failures, retry exhaustion, pagination restrictions, and incomplete
  retrieval by provider, paper, and direction;
- configured collection budgets, consumption, each budget-hit location, saved
  continuation cursor when available, and estimated/known uncollected counts;
- count and provenance summary of unprocessed candidates at stop time;
- edge-completion coverage by success, partial, failed, or unsupported status;
- topic annotation coverage, unclassified count, model, and scoring settings;
- whether the attempted traversal was fully processed or partial because of a
  user stop, provider restriction/failure, or 1,000-paper application limit.

Retrieval completeness means only that the application processed everything a
provider exposed for the configured traversal. It is distinct from coverage of
scholarly literature, which the application cannot guarantee.

## 5. Backend API

Initial endpoint contract:

| Method | Path | Responsibility |
| --- | --- | --- |
| `POST` | `/api/runs` | Validate input, create run, begin resolution/discovery |
| `POST` | `/api/topic-search` | Run a bounded Boolean paper search for seed review |
| `GET` | `/api/runs/{id}` | Return status, progress, warnings, and errors |
| `POST` | `/api/runs/{id}/continue` | Resume a run paused at 500 papers |
| `POST` | `/api/runs/{id}/stop` | Stop discovery and finalize retained data |
| `GET` | `/api/runs/{id}/graph` | Return explorer-ready nodes and edges |
| `GET` | `/api/runs/{id}/exports/{name}` | Download an allowed generated artifact |
| `POST` | `/api/import` | Validate uploaded canonical CSVs for exploration |
| `GET` | `/api/health` | Report application health |

Progress polling is sufficient for v1. Server-sent events or WebSockets may be
added later without changing the run model.

API errors use structured codes and user-readable messages. Run IDs and export
names are validated to prevent arbitrary filesystem access.

## 6. Frontend flow

### Study Configuration

- Repeatable seed input supporting pasted identifiers/URLs and PDF upload.
- Alternate topic-search mode with Boolean query syntax, explicit result limits,
  candidate review, and selection of one or more papers as graph seeds.
- Repeatable topic entry.
- Inclusive minimum/maximum year, direction, and depth controls.
- Inline validation plus this prominent limitation notice:

  > This application discovers papers through citation relationships with the
  > supplied seed papers. Relevant publications without a discovered citation
  > path to the seeds may be omitted.

### Discovery Progress

- Run state, resolved seed count, papers by depth and seed frontier, forward and
  backward candidate counts, nodes, edges, exclusions, retrieval completeness,
  and recoverable provider errors.
- At 500 papers, a blocking warning explains expansion cost and offers Continue
  or Stop and finalize.
- The continue dialog explicitly states that 1,000 papers is the final hard
  limit and that reaching it returns a partial graph containing everything
  retained up to that point.

### Citation Graph Explorer

- Cytoscape directed network with pan, zoom, fit, selection, and basic layout.
- Paper detail panel emphasizing the publication: title, authors, year, venue,
  DOI/publication URL, available abstract, assigned topics and similarity
  scores, incoming citations and outgoing references within the discovered
  graph, seed status, discovery depth, and provenance.
- Non-destructive filters for year, topics, minimum relevance, seed status,
  internal/provider citation count, graph distance, and text search.
- Filter state changes the rendered subgraph only; it never rewrites imported or
  generated datasets.
- A clear badge identifies stopped or hard-limited partial runs.
- Provider-limited and retrieval-incomplete runs are also visibly distinguished
  from fully processed attempted traversals.

### Discovered Papers

- Provide a dedicated searchable and sortable publication list linked
  bidirectionally with the graph explorer.
- Emphasize publication year, title, authors, seed/discovered status, discovery
  depth, assigned topics, and topic-similarity scores.
- Default to newest publication year first, with controls for topic relevance,
  year, and discovery depth. The list uses the same non-destructive filter state
  as the graph.
- Selecting a list row opens that paper's details and focuses its node in the
  graph; selecting a graph node highlights and scrolls to its list row.
- Provide a list-first usable view when a graph is too dense or a paper lacks
  enough relationships to be visually prominent.

### Export

- Separate downloads for both CSVs, optional GraphML, and run metadata.
- Summary of warnings and exclusions before download.
- Explorer import for a matching `papers.csv` and `citations.csv` pair without
  any provider request.

## 7. Implementation phases

### Phase 0 — Project foundation

- Scaffold FastAPI and React/TypeScript applications.
- Add shared development commands, environment template, formatting, linting,
  tests, Docker Compose, and generated-data ignores.
- Define domain models, API schemas, durable SQLite schema/migrations, job lease
  protocol, status machine, and CSV contracts.

Exit criterion: both applications run locally, health checks pass, and CI can
execute empty test suites and static checks.

### Phase 1 — P0 discovery and canonical exports

- Implement seed parsing, keyless provider adapters, resolution, strict year
  enforcement, depth-ordered BFS, deterministic candidate ordering, balanced
  seed-frontier scheduling, deduplication, and provenance.
- Implement transactional checkpoints, restart recovery, and idempotent job
  execution before enabling long discovery runs.
- Implement the 500 pause/continue/stop workflow and 1,000-paper hard limit.
- Complete internal edges and generate `papers.csv`, `citations.csv`, and
  `run_metadata.json`.
- Build configuration and progress screens.

Exit criterion: fixture-backed integration tests perform a bidirectional,
multi-hop run with valid, duplicate-free exports, survive forced restarts, and
exercise all limit and provider-incompleteness behaviors.

### Phase 2 — P0 explorer

- Load generated or uploaded canonical CSVs.
- Render the Cytoscape graph, details, directionality, search, and basic filters.
- Build the linked Discovered Papers list with year- and topic-focused sorting.
- Ensure filters leave source records unchanged.

Exit criterion: exported fixtures reconstruct the expected graph without any
OpenAlex call.

### Phase 3 — P1 topic annotation and reporting

- Add the local embedding pipeline, multi-label scores, unclassified handling,
  and topic/relevance filters.
- Expose exclusions, warnings, provider failures, and classification limitations
  throughout progress, explorer, and metadata output.

Exit criterion: deterministic test embeddings verify multi-label assignment and
no paper is removed due to topic relevance.

### Phase 4 — P2 interoperability and hardening

- Add GraphML export, accessibility work, larger graph performance tuning,
  cancellation checks, request throttling, and documentation.
- Verify all acceptance criteria and add an end-to-end happy path.

Exit criterion: acceptance test matrix passes and a clean checkout can run via
documented local commands.

## 8. Test strategy

OpenAlex responses are recorded as small, curated fixtures; automated tests do
not depend on live network availability.

### Backend unit tests

- Identifier parsing and normalization.
- Conservative identity matching and deduplication.
- Direction semantics and strict BFS depth ordering.
- Deterministic candidate sort keys, forward/backward merging, and deduplication.
- Balanced deterministic round-robin scheduling across seed frontiers.
- Inclusive year boundaries and missing-year exclusions.
- Directed-edge uniqueness and completion.
- State transitions at 500 and 1,000 papers.
- Checkpoint serialization, transactional recovery, lease expiry, and idempotent
  replay.
- Topic scoring, thresholding, and unclassified cases.
- CSV escaping, JSON-in-CSV fields, GraphML generation, and path safety.

### Backend integration tests

- Multiple seed resolution with partial failures.
- Backward, forward, and bidirectional traversal through three hops.
- Stop at the warning and continue to the hard limit.
- Restart the application while discovering and while paused, then resume
  without duplicated nodes, edges, or skipped candidates.
- Transient provider failure and rate-limit retries.
- Restricted pagination, partial frontier ordering, PDF backward-only fallback,
  and graceful fallback failure.
- Per-query, per-depth, and per-run collection-budget exhaustion with explicit
  coverage metadata and restart-safe saved cursors.
- Referential integrity across all exports.

### Frontend tests

- Form validation and limitation disclosure.
- Progress counters and warning actions.
- Keyless-provider restriction and incomplete-retrieval disclosures.
- Filter combinations and non-destructive behavior.
- Search by title, author, DOI, and provider ID.
- Linked selection and shared filter state between Discovered Papers and graph.
- Partial-run labeling and artifact downloads.

### End-to-end tests

- Configure a fixture-backed run, pause/continue, explore, filter, and export.
- Import the resulting CSV pair into a fresh explorer session and compare graph
  nodes and edges.
- Verify the import path makes no external scholarly-provider request.

## 9. Operational and product safeguards

- Use bounded HTTP concurrency, explicit timeouts, retry budgets, and descriptive
  user-agent headers.
- Never claim complete scholarly coverage; display the required citation-source,
  topic-uncertainty, disconnected-paper, and expansion-cost limitations.
- Report provider page caps, blocked pagination, unsupported directions, and
  fallback failures rather than treating a truncated result as complete.
- Sanitize uploaded filenames and CSV content, cap upload sizes, and neutralize
  spreadsheet formula cells in exports.
- Avoid logging abstracts, uploaded PDF contents, or sensitive request headers.
- Pin the embedding model version and Python/Node dependencies.
- Treat OpenAlex schema drift and outages as recoverable provider failures where
  partial results can still be finalized.
- Restrict public-page and PDF retrieval to permitted URLs and safe content
  types; protect against server-side request forgery, oversized downloads, and
  malicious documents.

## 11. Changes in this revision

- Reframed the product around discovering research literature, particularly
  recent papers, rather than bibliometric or influence analysis.
- Replaced in-memory run state with durable SQLite checkpoints and restart-safe,
  idempotent worker execution as an MVP requirement.
- Added deterministic per-frontier prioritization by ascending provider citation
  count, descending year, and stable identifier, plus round-robin balance across
  seed frontiers while preserving BFS depth.
- Expanded the keyless provider design with arXiv metadata and local public-PDF
  reference extraction as backward-discovery fallbacks.
- Made provider truncation, pagination restrictions, edge-retrieval status, and
  unprocessed candidates first-class provenance and reporting fields.
- Clarified that edge completion covers retrieved provider data, not every
  real-world citation, and that topic similarity is heuristic rather than a
  probability.
- Expanded the paper detail view and progress reporting to emphasize discovered
  publications and their provenance.
- Added bounded candidate collection at per-query, per-depth, and per-run levels,
  with explicit budget-consumption and incomplete-coverage reporting.
- Added a dedicated newest-first Discovered Papers list with shared filters and
  bidirectional selection linking it to the citation graph.

## 12. Known limitations and unresolved technical risks

- OpenAlex and every fallback can omit works or citations. Even a run marked
  fully processed is complete only relative to data exposed during the attempted
  traversal, never the scholarly record.
- Keyless endpoints may change rate limits, schemas, pagination policies, or
  access without notice. The application can report and degrade around these
  conditions but cannot eliminate them.
- Conservative candidate budgets intentionally trade breadth for predictable
  keyless-provider usage. Budget-capped runs are retrieval-incomplete even when
  no provider error occurred.
- Sealing a frontier before deterministic sorting may require retrieving and
  storing many more candidates than the 1,000-paper retention limit. Disk use,
  request cost, and latency need measurement with realistic fixtures.
- Provider-reported citation counts can be missing, stale, or inconsistent. They
  affect traversal order only and must not be interpreted as relevance.
- Balanced frontier attribution becomes many-to-many when papers are reachable
  from several seeds. Shared-credit reporting is defined, but UX for presenting
  it needs validation.
- Conservative reference resolution reduces false matches but leaves some PDF
  references unresolved; GROBID extraction quality varies by document layout.
- Public PDF retrieval introduces security and resource risks and needs strict
  URL, redirect, size, timeout, and content validation.
- SQLite and a single-worker lease model target local/single-instance use. A
  multi-process or hosted deployment would require stronger coordination and is
  deferred.
- Local sentence-embedding model download, CPU cost, licensing, version pinning,
  and offline packaging must be confirmed during project setup.
